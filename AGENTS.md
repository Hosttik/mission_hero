# Mission Hero — инструкции для всех агентов

Этот файл обязателен для Codex, ChatGPT и любого следующего исполнителя. Работа **последовательная**: в каждый момент один исполнитель. История личного чата и память конкретного агента не считаются источником истины.

## Главная цель

Создать за ориентировочные 3–5 недель тестовый веб-прототип Mission Hero — интерактивный космический корабль для детей 4–7 лет, рассчитанный преимущественно на игру в комнате, с 10–15 событиями и реальным тестированием с семьями. Продажи, другие миры, облачная синхронизация и runtime-LLM не входят в текущий этап.

## Порядок чтения при каждом входе

1. Этот файл.
2. `docs/PROJECT_STATE.md` — текущая фаза, активная задача, ветка/PR, блокировки.
3. `docs/HANDOFF.md` — конкретный контекст последнего исполнителя.
4. `docs/TASKS.md` и `docs/ROADMAP.md` — очередь, зависимости, критерии.
5. `docs/DECISIONS.md` и релевантные разделы `docs/PRODUCT.md` — требования.
6. `docs/COLLABORATION.md` — как работать через GitHub из Codex и ChatGPT.
7. Проверь фактическое состояние Git: ветку, diff, последние коммиты и открытые PR по текущей задаче.

Если работаешь локально, перед чтением статуса выполни `git fetch origin` и безопасно обнови свою ветку; не теряй незакоммиченные изменения. Если работаешь через GitHub API, читай свежий `main`, затем активную ветку/PR. Ни один агент не должен предполагать, что видит чужие незапушенные изменения.

## Начало работы

- Уточни актуальную задачу по её ID (`MH-XXX`). Не начинай новую задачу, пока предыдущая имеет незавершённый handoff или неясный статус.
- Проверь зависимости и критерии готовности. Если задача неоднозначна, сначала предложи минимальное разрешение противоречий, а не выдумывай требования.
- Зафиксируй `active_agent`, `active_task`, `active_branch` и состояние задачи **в общем репозитории**. Для значимых кодовых изменений используй ветку и PR; состояние/передача контекста публикуются в `main`.
- Если задача принадлежит другому активному агенту, остановись и попроси передачи. Автоматических параллельных захватов задач нет.
- Перед разработкой проверь завершение инфраструктурного аудита `MH-014`. В рамках MH-014 выполняй только настройку и её проверку; не переходи к игровой задаче без нового поручения.

## Простое правило состояния

- На входе: fetch, безопасная синхронизация, чтение документов и `git status`; затем опубликуй исполнителя, ID и ветку в `main` до основной работы.
- При смене задачи, существенном изменении плана, блокере или открытии PR: вместе обнови PROJECT_STATE и TASKS; при необходимости оставь промежуточный HANDOFF.
- На выходе: проверь критерии, запиши фактические команды/результаты, проблемы и следующий шаг; commit + push; проверь удалённый SHA. Сними активного исполнителя только после checkpoint.
- Незавершённая задача сохраняет ID и статус REVIEW/BLOCKED/READY с объяснением; следующий агент продолжает её прежде взятия новой. READY допустим при добровольной передаче незаконченной работы с ясным handoff. Недоступный push — передача не завершена.
- `active_agent`, `active_task`, `active_branch`, `next_task`, `last_verified_commit` ведутся в PROJECT_STATE. Последний проверенный SHA относится к конкретным проверкам; SHA самого handoff получают через Git, чтобы не создавать самоссылку.
- Один исполнитель, одна задача. Не нужны распределённые блокировки, фоновые исполнители, автоматические очереди или параллельные worktree. Агентская активность в документе — договорённость, а не lock-сервис.

## Во время работы

- Выполняй одну задачу за раз. Не расширяй функциональность за пределы критериев готовности без согласования.
- Обновляй общее состояние при смене цели, значимом блокере, открытии PR и перед завершением. Если сессия обрывается, по возможности отправь промежуточный checkpoint.
- Отделяй подтверждённое требование `[Р]` от предложения `[П]` и гипотезы `[Т]` в продуктовом ТЗ. Пользовательские решения нельзя без согласования превращать в противоположные.
- Пиши тесты на правила игры и сохраняемое состояние; описывай команды и результаты проверок. Нельзя заявлять `tests passing`, не запустив проверки.
- Не коммить секреты, рабочие ключи, приватные данные детей или персональные данные тестовых семей. Не устанавливай внешние агенты/хуки, меняющие глобальные настройки, без разрешения.

## Передача следующему агенту — обязательно

1. Закоммить и **запушь** все предназначенные для передачи изменения или явно укажи, что осталось локально и потому не передано.
2. Укажи ветку, SHA, PR, затронутые файлы, проверенные команды и результаты.
3. Обнови `docs/TASKS.md` (задача `DONE` только после выполнения критериев и попадания согласованного результата в основную ветку).
4. Обнови `docs/PROJECT_STATE.md`: актуальный статус, следующая конкретная задача, блокировки, ссылка на PR/ветку.
5. Перепиши `docs/HANDOFF.md`: что сделано, почему приняты решения, что осталось, где начать следующему агенту.
6. Сообщи пользователю, что работа передана; историю чата нельзя использовать как замену пунктам выше.

## Источники и конфликты

По приоритету: последнее явное решение пользователя → `docs/DECISIONS.md` (подтверждённые решения) → разделы `[Р]` в `docs/PRODUCT.md` → `docs/ROADMAP.md` и `docs/TASKS.md` → технические предложения. При противоречии зафиксируй его в handoff и запроси решение; не меняй продукт незаметно.

## Границы этой инфраструктуры

Agent Relay, если подключён к среде Codex, — оперативные сообщения. Для ChatGPT общий мост — GitHub. Обновления без `git push` не доступны другим средам. Полный протокол и ограничения см. `docs/COLLABORATION.md`.

## Версии и публикация — обязательное правило

- Перед **каждым новым релизом на GitHub Pages** увеличь SemVer в `VERSION` и `package.json` и добавь раздел новой версии в `CHANGELOG.md`.
- Публикация выполняется только workflow GitHub Actions после изменения `VERSION` в `main`. Изменения без повышения версии не должны публиковаться.
- Прежде чем сообщить об успешном релизе, проверь Actions и доступность опубликованной страницы; не путай успешную сборку с успешным деплоем.
- Не запускай альтернативный Pages deploy в обход version gate. Исключение — повторная публикация уже зафиксированного идентичного релиза при техническом сбое.
- Подробности: `docs/RELEASES.md`. Обновляй `docs/PROJECT_STATE.md` и handoff только на основании фактического статуса деплоя.
