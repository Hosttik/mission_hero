# Координация Codex ↔ ChatGPT

## Реально доступный механизм

Оба исполнителя работают с одним GitHub-репозиторием: `Hosttik/mission_hero`.

- **Codex в локальном репозитории:** `git fetch/pull` для получения чужих изменений, `commit + push` для публикации своих. Ветка/PR — для функциональных изменений.
- **ChatGPT в чате с подключённым GitHub:** читает репозиторий и PR; при наличии write-доступа может изменить файлы через GitHub API, создать ветку и PR. Если подключение только для чтения, передаёт конкретные правки исполнителю с write-доступом и не объявляет их опубликованными. У него **нет автоматического доступа к незапушенному рабочему дереву Codex**.
- **Agent Relay (опционально):** быстрые STATUS/BLOCKED/DONE и уведомления между подключёнными клиентами; не заменяет Git и перечисленные документы. **Прямой мост между этим чатом и Relay сейчас не установлен.** Не утверждай, что сообщения Relay сами доходят в ChatGPT.

Чтение актуального опубликованного состояния возможно сразу после успешного push/API-коммита. **Это не потоковая трансляция ещё не опубликованных локальных изменений.**

## Единственный активный исполнитель

Согласно решению владельца проекта, агенты **не работают одновременно**. Нет автозахвата задач и гонки за файлы. Перед сменой исполнителя обязателен checkpoint.

## Источники истины

| Что | Где |
| --- | --- |
| Требования | `docs/PRODUCT.md`; метки `[Р]` / `[П]` / `[Т]` |
| Подтверждённые решения | `docs/DECISIONS.md` |
| Этапы | `docs/ROADMAP.md` |
| Очередь и статусы задач | `docs/TASKS.md` |
| Текущая активная задача, ветка/PR и блокеры | `docs/PROJECT_STATE.md` в `main` |
| Передача контекста | `docs/HANDOFF.md` в `main` |
| Фактический код | Коммиты/ветки/PR GitHub, а не слова агента |

## Протокол получения задачи

1. Прочитать свежий `main`: `AGENTS.md`, PROJECT_STATE, HANDOFF, TASKS.
2. Проверить текущий активный PR/ветку и фактический HEAD.
3. Убедиться, что предыдущий исполнитель завершил передачу; при незакрытой активной задаче запросить подтверждение takeover.
4. Изменить на `main` статус задачи и поля текущего исполнителя. Зафиксировать ожидаемый результат и ветку.
5. Выполнить работу в собственной ветке, запушить результат, открыть PR для ревью/CI. При необходимости приложить screenshots/артефакты или результаты тестов.
6. Зафиксировать актуальный статус на `main`, включая PR/ветку и handoff. Не ссылаться на недоступный локальный контекст.

**Схема состояний:** `BACKLOG → READY → IN_PROGRESS → REVIEW → DONE`; `BLOCKED` временно допустим из любого незавершённого состояния. `DONE` — проверено и интегрировано. Нельзя считать `REVIEW` завершением.

## Передача работы ChatGPT

Пользователь может написать: «Возьми MH-005 в Hosttik/mission_hero» или «Проверь PR #N». ChatGPT должен прочитать последнее состояние проекта, не опираясь лишь на этот чат; внести правки в ветку/PR через GitHub; указать, какие тесты реально выполнялись; обновить handoff и состояние.

Для больших задач, которые требуют локальной сборки, ChatGPT может подготовить PR через GitHub и оставить его в REVIEW, если не смог запустить проект. Codex затем проверяет сборку и завершает интеграцию.

## Передача работы из Codex

Перед выходом из активной сессии Codex публикует весь передаваемый код в GitHub. Если текущая работа незакончена — отправляет WIP-ветку, указывает её точный commit SHA и конкретные незавершённые файлы/проверки в HANDOFF. Если GitHub недоступен, исполнитель **не отмечает передачу как состоявшуюся**.

## Checkpoint и смена исполнителя

Минимум состояния в PROJECT_STATE: `active_agent`, `active_task`, `active_branch`, PR (или «нет»), `last_verified_commit`, `next_task`, блокеры. В HANDOFF: цель, что сделано/не сделано, SHA/ветка, файлы, команды с результатами, ограничения и одно конкретное следующее действие. Продуктовые решения не дублировать целиком — давать ссылки.

Только документальные изменения допускаются прямо в `main`. Для значимых изменений кода обязательны ветка `codex/...` и PR. Во время работы в ветке состояние на `main` можно обновить через GitHub API или последовательно переключившись при чистом рабочем дереве; параллельный worktree не нужен. После этого вернуть рабочую ветку и получить актуальный `origin/main` перед интеграцией. Не потерять незакоммиченные файлы; не применять reset/force push ради синхронизации.

При конфликте локальной ветки с remote остановить правку затронутых файлов, изучить diff и сохранить оба результата до разрешения. Если активный исполнитель не завершил передачу — запросить её у владельца; отсутствие свежего сообщения не означает освобождение задачи.

На выходе сначала push кода/checkpoint, затем публикация итогового HANDOFF/PROJECT_STATE/TASKS и проверка удалённого SHA. При сбое финального push состояние ещё не передано. `last_verified_commit` — SHA проверенного содержимого до метаданных handoff; текущий SHA handoff можно получить через `git rev-parse HEAD` или GitHub. Последний документальный коммит не объявлять автоматически проверенным игровым релизом.

## Agent Relay: только уведомления

Проверены официальный релиз 14.0.0 и исходники по фиксированному SHA; подробный обзор затрагиваемых файлов, hooks, прав, ключей и отката — [RELAY_SETUP.md](RELAY_SETUP.md). Конфигурация-пример не активирована. Relay не установлен и не подключён; MH-015 ожидает согласования. Доставка сообщений не проверялась.

Если подключение согласовано и проверено, один активный исполнитель публикует в канале `mission-hero-status`:

```text
STATUS | agent=Codex | task=MH-002 | branch=codex/mh-002 | sha=<pushed SHA>
PROGRESS | task=MH-002 | checked=<результат> | next=<действие>
BLOCKED | task=MH-002 | reason=<причина> | need=<что требуется>
DONE | task=MH-002 | sha=<интегрированный SHA> | checks=<результат> | next=MH-003
```

STATUS — после принятия задачи; PROGRESS — при значимом checkpoint; BLOCKED — при блокере; DONE — только после критериев и интеграции. При выходе с незавершённой работой — STATUS с `handoff=REVIEW/BLOCKED/READY`, веткой/SHA и следующим шагом. Перед сменой исполнителя всё равно обязательны push и документы на GitHub. Если Relay недоступен, записать это в HANDOFF и продолжать GitHub-протокол. Не выдавать успешный вызов отправки за доказательство чтения сообщения.

Ни hooks, ни Relay-сообщения не разрешают запуск второго исполнителя. Не пересылать секреты, исходники целиком, историю чатов или данные семей. Внешний ChatGPT без Relay-клиента читает GitHub; уведомления в него автоматически не приходят.

## Как понять, что схема работает

Новый агент в совершенно новом чате/сессии, получив только имя репозитория, обязан без уточняющих вопросов определить: цель MVP, актуальный этап, ближайшую READY-задачу, активную ветку или PR, блокировки, результаты последних проверок, следующий конкретный шаг.
